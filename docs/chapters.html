RISC-V • SystemVerilog • A growing processor laboratory

Build an out-of-order processor, one invariant at a time.

This tutorial begins with clocked digital logic and reaches the design choices behind speculative, superscalar processors. Its executable starting point is a deliberately small out-of-order integer backend. Read the explanations alongside the RTL appendix: every implemented module is included in this document, without an internet dependency.

Scope and evidence. The supplied RTL is milestone 0, not a complete RISC-V processor. Later chapters are design lessons and implementation plans, not claims that those features exist in the code. “Modern” describes relevant techniques, not a single required combination. No finite tutorial exhausts every processor architecture or research algorithm. This document explains the mechanisms it introduces and gives a staged path for expanding this repository.

02 · Bits, clocks and architectural state

A combinational circuit computes outputs from its present inputs. A register remembers a value across clock cycles. RTL describes both concurrently; it is not a program that executes one source line per clock. During a cycle, combinational signals settle. At a rising edge, each register captures its selected next value. A path that fails to settle before the setup deadline can violate timing even when functional simulation passes.

A 32-bit word is a bit vector. Addition produces the low 32 bits in this design; carry beyond bit 31 is discarded. Signed two's-complement interpretation gives a high-bit-set word a negative value. The bit pattern is unchanged by interpreting it as signed: only operations such as comparison and right shift differ. Logical right shift inserts zeros; arithmetic right shift repeats the sign bit. A register index is a name, not the value inside that register.

The instruction set architecture (ISA) is the contract visible to software: instruction encodings, register effects, memory behavior and exceptions. Microarchitecture is the hardware mechanism that fulfills that contract. Two implementations can execute the same binary while using different pipelines, caches, queues and prediction schemes. Out-of-order execution changes internal timing; it must preserve required architectural behavior.

Architectural state includes committed registers and, in a complete machine, memory effects and privileged state. Speculative state represents work not yet guaranteed to belong to the accepted execution path. In this baseline the committed integer register array lives in rename.sv; computed but unretired values live in ROB entries. A value being available is therefore different from a value being committed.

The laboratory clears all registers on reset for reproducibility. This is a local interface choice, not a claim that the ISA defines every general-purpose register's reset value. Reset is synchronous: changing rst_i alone does not immediately clear the registers; a rising edge is required.

03 · RISC-V instruction mechanics

RV32I uses 32-bit integer registers, with x0 fixed at zero. Encodings place the destination in bits 11:7, source 1 in 19:15, and source 2 in 24:20 when those fields apply. R-type instructions use two registers; I-type arithmetic instructions use a sign-extended immediate. U-type instructions carry an upper immediate. Other formats rearrange immediate bits for stores and control flow. Use the versioned RV32I specification as the encoding authority.

Implemented familyOperationsDecoder responsibility
Register arithmeticADD, SUB, SLL, SLT, SLTU, XOR, SRL, SRA, OR, ANDSelect operation; validate funct7; bind both source registers.
Immediate arithmeticADDI, SLTI, SLTIU, XORI, ORI, ANDI, SLLI, SRLI, SRAIReplace operand B with the immediate; validate shift encoding.
Upper immediateLUI, AUIPCUse zero or supplied PC as A; use bits 31:12 followed by twelve zeros as B.
Everything elseBranches, jumps, loads, stores, fences, system operations and extensionsEmit the laboratory's unsupported-instruction fault.

For addi x2,x1,-1, the decoder extracts x1, x2 and the immediate, then creates 0xffffffff for operand B. For srai, the ALU uses the low five bits as the shift amount. SLTIU still receives a sign-extended immediate before doing an unsigned comparison. LUI and AUIPC must not wait for register fields that happen to occupy immediate bits. The ROB operand overrides explicitly prevent that false dependency.

Rejecting an unsupported encoding is safer than accidentally executing it as ADD. The decoder validates function fields; for example an M-extension multiplication encoding must not silently become integer addition. The terminal fault used here is a laboratory protocol, not RISC-V architectural trap entry.

Pipeline depth, issue width and instruction ordering are different axes. The supplied core can issue only one instruction per cycle and is still out of order: a ready younger instruction can pass an unready older one. Its execution pipeline has an initiation interval of one cycle but a result latency of three registered stages. Adding pipeline registers does not automatically increase useful work per cycle.

05 · Dependencies, scoreboarding and Tomasulo-style scheduling

A: addi x1, x0, 10
B: addi x2, x1, 1
C: addi x3, x0, 7
D: addi x1, x0, 99
E: add  x4, x2, x1

B has a read-after-write (RAW) dependency on A: B needs A's value. D creates a write-after-write (WAW) name conflict with A, and a write-after-read (WAR) name conflict with B. D need not wait for B if B has already bound its source to A's particular result. C is independent and may execute while B waits. E must use B's result and D's result, not whichever write to x1 happens to complete most recently.

A scoreboard tracks resource availability and pending reads/writes to determine when execution is safe. Without renaming, name hazards constrain when reads and writes may proceed. Tomasulo-style scheduling instead associates unavailable operands with producer tags and wakes waiting operations when tagged results arrive. Renaming removes false name dependencies; it does not remove RAW dependencies. The tutorial core uses this tagged-dataflow idea with a ROB to keep retirement ordered.

At dispatch, a ready operand carries a value; an unready operand carries the producer's ROB tag. That binding never changes merely because another instruction later writes the same architectural name. On broadcast, matching consumers capture the value and become ready. The architectural name x1 is used during binding; the scheduler waits on the bound tag. This distinction is the reason younger writers cannot corrupt an older reader.

For this eight-entry machine, tags are only three bits. A tag is not a permanent instruction identifier. It may be reused after its entry retires. This is safe here because completion occurs before retirement, all waiting consumers capture completion, and dispatch can read an already-completed result. Branch cancellation or asynchronous memory responses would invalidate that simple argument and require cancellation or generation tracking.

06 · The executable architecture

Instruction + PC→ Decode→ Rename→ ROB / operands→ Oldest-ready issue→ ALU pipeline→ Broadcast→ Ordered retirement

The ROB contains eight entries with valid, issued, done and illegal flags; PC and original instruction; destination register; ALU operation; two operand records; and result data. Allocation appends at the tail. Retirement removes the head. Issue scans the live window in age order and can select any ready unissued entry. A single physical structure thus serves both as the reorder buffer and a reservation station. Later designs can split them without changing the logical responsibilities.

The rename module stores 32 committed values plus a speculative map. If a register is mapped, its newest writer is still represented by a ROB tag. If not mapped, the committed register value is ready. x0 is never mapped or written. The execution pipeline accepts one selected operation every cycle, computes the ALU result, and delays its tagged result through three registers. A single broadcast can wake multiple consumers.

There is no program counter register in the core. The caller supplies each PC alongside its instruction. This makes the backend independently testable and prevents a placeholder fetch block from suggesting a complete processor. The supported instruction stream is straight-line integer computation. The larger CPU will eventually connect a frontend to this interface, then add redirect and fault protocols.

07 · SystemVerilog state and logic discipline

state_t state_q, state_d;

always_comb begin
  state_d = state_q;             // Hold by default.
  if (event_i) begin
    state_d.field = new_value;   // Combinational next-state selection.
  end
  if (rst_i) state_d = '0;       // Synchronous reset selection wins.
end

always_ff @(posedge clk_i) begin
  state_q <= state_d;            // Assignments only, as requested.
end

Blocking assignment in the combinational block allows later statements to use earlier intermediate values. Nonblocking assignment in the sequential block models registers updating together at an edge. Defaulting next state to current state expresses a hold condition; it does not infer a latch because every next-state bit receives a value. Outputs and local combinational temporaries also need defaults on every path.

The reset condition belongs in the combinational block in this repository. Consequently the sequential blocks contain no conditions, cases, loops, arithmetic or reset branches—only the state transfer. This convention describes a synchronous reset. It must not be casually converted to an asynchronous sensitivity list, because clearing state without an edge is a different hardware contract.

Packed structures make small state bundles readable and support whole-state assignment. They are not instructions to build every future memory from resettable flip-flops. A physical register file or cache intended for FPGA block RAM or ASIC SRAM needs the target memory's port, latency, initialization and collision semantics. Keep those target decisions behind a documented module boundary.

Explicit casts such as tag_t'(distance) document intentional truncation for the power-of-two circular buffer. The signed casts in the ALU document signed comparison and arithmetic shifting. A lint-clean design is valuable, but lint alone cannot prove instruction semantics or timing. The repository also checks that sequential bodies retain this exact style.

08 · Package, decoder and ALU walkthrough

ooo_pkg.sv defines the shared vocabulary. word_t is data, reg_t is an architectural name, and tag_t identifies a live ROB producer. decoded_t describes operation intent, operand_t describes a value or pending producer, entry_t owns an instruction's lifetime, and result_t carries a completion. Keeping these concepts in distinct types reduces accidental mixing.

decode.sv begins with a complete default record. It extracts register fields and a signed immediate, then chooses the opcode family. Arithmetic function bits select an ALU operation. Upper-immediate instructions explicitly select zero or PC. Finally, legality checks distinguish supported encodings from unsupported ones. It has no clock, storage or backpressure; the top-level admission handshake determines when its outputs matter.

alu.sv is pure combinational computation. All operations produce a 32-bit result. Comparisons produce a single Boolean in bit zero with zeros above it. Right shifts differ only in signedness; left and right shifts mask B to five bits. There are no carry flags or arithmetic overflow traps. Operation defaults prevent incomplete assignments if an enum value is outside the supported set.

To add an arithmetic operation, define its semantics first, add the decode legality condition, implement its data operation, and add an independent reference check. A multi-cycle divider additionally requires a functional-unit availability protocol and completion arbitration; placing division in this ALU case statement does not by itself produce a practical divider implementation.

09 · Rename module and same-register races

rename.sv contains mapped, tags and registers arrays. A source lookup returns ready when its mapped bit is clear. When mapped, its tag points to the newest older producer. Allocation installs the incoming destination tag unless the destination is x0. Illegal instructions do not allocate a rename mapping because they will never create an architectural result.

Source reads use state_q, not the just-updated map. For addi x1,x1,1, the source must refer to the previous writer while the destination becomes a new writer. Reading next state after allocation would create a self-dependency and deadlock. This is a common failure that a simple isolated ADD test does not expose.

Commit always writes the architectural value for a nonzero destination. It clears the speculative mapping only if the mapping still names the committing tag. Suppose A and D both write x1, with D younger. When A commits, x1's architectural value becomes A's result, but the speculative map must continue to name D. When D commits, its map can clear if no still-younger writer has taken ownership.

Retirement is applied before allocation in next-state construction. If both name x1 in the same cycle, the new instruction wins the mapping. Source lookup still sees the old map and can obtain the retiring producer's completed value from the old ROB entry. This explicit old-state/new-state distinction avoids relying on simulator statement order between modules.

10 · ROB, wakeup and ordered retirement

rob.sv owns instruction lifetime. head identifies the oldest live entry, tail identifies the next empty allocation position, and count distinguishes full from empty when pointers match. Count ranges from zero through eight, so it needs four bits. Head and tail use three bits and naturally wrap modulo eight.

Incoming operands first resolve against completed ROB entries. Next, the current result broadcast can satisfy a still-pending incoming operand or any existing consumer. Immediate and PC overrides are then applied. This order means a consumer cannot miss a producer that completes on exactly its dispatch cycle. Without the incoming broadcast path, it could store a tag after the producer's only broadcast and wait forever.

Issue marks an entry issued but leaves it resident. Completion marks it done and stores the result. Retirement is permitted only when the head is done and the receiver is ready. A completed younger entry cannot pass an unfinished head. Architectural register updates occur on the accepted retirement event, not on completion.

When both dispatch and retirement occur, next-state count decreases and then increases, producing no net change. The full-buffer case deliberately does not accept a replacement dispatch even when the head retires; this introduces a possible bubble but removes a same-slot overwrite corner case. An optimization may change this only after defining and testing the priority among old-head reads, result writes, entry clearing and new allocation.

A faulting entry is allocated already done. It does not issue and cannot write committed registers. At the head it exposes a fault event and stops new issue/admission. Once the event is accepted, halted state prevents further retirement until reset. This gives an ordered terminal stop for the test harness. It does not implement trap CSRs, redirect, architectural exception codes, or resumable recovery.

11 · Issue selection and execution timing

issue_select.sv scans distance zero through seven from the head. An entry requests issue when valid, not already issued, not illegal and both operands ready. The first requesting entry wins. Raw numeric tag ordering would fail after wraparound: tag 0 can be younger than tag 7. Head-relative scanning preserves program age.

execute.sv computes the selected ALU value and shifts a result record through three registers. Every cycle can accept another operation. This is a pedagogical latency, not a synthesis result or a claim that addition needs three cycles. A real timing-driven pipeline would partition the datapath and justify register placement with synthesis and timing reports.

Selection reads current ready bits. Broadcast writes next-state ready bits, so a woken consumer becomes eligible in the following cycle. There is no combinational broadcast-to-select-to-ALU bypass. This increases dependency latency but keeps the scheduling path easy to inspect. A fast bypass design needs correctly timed data as well as an early readiness indication.

12 · Handshakes, simultaneous events and invariants

A valid/ready channel transfers only at an edge with both signals asserted. The producer must keep payload and valid stable while valid is high and ready is low. The retirement receiver may stall the machine indefinitely; eventual completion is only expected when it eventually accepts work. Outputs with valid low have no payload meaning.

Fault at head + younger workNo new issue or allocation; younger work cannot retire.

Useful invariants are: occupancy never exceeds eight; a live instruction issues at most once; every normal retirement was allocated; retirement order equals allocation order; x0 remains zero; a rename mapping names the latest live writer; and an unready operand's tag names a producer whose value has not been captured. Translate these into assertions as the verification environment expands. In particular, liveness properties must state fairness assumptions about downstream readiness.

When adding redirects, introduce a priority table before coding. An older exception, a younger branch misprediction and a memory-order replay may occur together. Select the oldest architecturally relevant recovery, kill only appropriate younger work, and reject late completions from killed instructions. Separate “stop accepting,” “kill pending work,” and “restore architectural state”; they are different actions.

13 · Verification: what passes and what remains

The supplied C++ test interprets each accepted instruction against a separate register array and queues its expected retirement. It checks PC, original encoding, destination, fault status and result when retirement occurs. Random instruction generation uses a fixed seed for repeatability, exercises all implemented operation families, and injects input gaps and retirement stalls. Directed instructions exercise dependency chains, multiple writers and x0.

The initial retirement stall pressures the queue. Tracking issue tags against outstanding allocation order detects duplicate/unallocated issue and confirms out-of-order selection. Repeated instruction streams wrap the ROB many times. Unsupported opcodes and invalid function encodings terminate scenarios, followed by reset and another run. See docs/validation.md for the exact executed version and results.

This is a functional regression, not a compliance certificate. A finite random run does not prove all bit patterns. A C++ interpreter can also contain bugs, so compare a later full CPU against an independent ISA simulator and architectural tests. Add explicit per-instruction and cross-event coverage counters, formal invariants, fault injection and constrained random programs as complexity grows. Test a bug with the smallest sequence that would have failed before the fix.

For a full core, record a retirement trace containing instruction, PC, source values, destination writes, memory effects and traps. An RVFI adapter can make formal comparison practical, but the current trace is not RVFI. Memory litmus tests are additionally required once concurrency and weak memory ordering exist. Architectural differential testing alone may miss an illegal externally visible speculative store.

Simulation does not establish synthesizability on a specific tool, maximum frequency, power, physical area, CDC correctness or FPGA operation. Those need their own reports and targets. The CI workflow executes the local regression on GitHub once pushed; creation of the YAML does not establish a successful remote run.

14 · Moving to a physical register file

Future implementation: the current design has no physical register allocator or free list.

Explicit renaming separates a large physical register file (PRF) from the ROB. An architectural name maps to a physical register; allocating a destination selects a free physical register and remembers the previous mapping. A busy table says whether each physical value is ready. The ROB retains ordering and recovery metadata rather than all result data. At retirement the overwritten old physical mapping can be reclaimed. BOOM's rename documentation describes this organization and its contrast with data-in-ROB renaming.

Design sketch, not current RTL:
old_dst = speculative_map[rd]
src1    = speculative_map[rs1]  # Read before replacing rd.
src2    = speculative_map[rs2]
new_dst = allocate_free_register()
speculative_map[rd] = new_dst
busy[new_dst] = true
ROB.append(rd, new_dst, old_dst, PC, ...)

on accepted completion: PRF[new_dst] = value; busy[new_dst] = false
on retirement:         reclaim(old_dst)

Keep physical zero permanently reserved. Stall dispatch atomically if either ROB space or a destination allocation is unavailable; partially allocating one structure leaks resources. With several dispatch lanes, later lanes must see earlier lanes' map updates. If two lanes write the same architectural name, the last accepted writer becomes the map entry, but each lane retains the correct old destination for reclamation.

Recovery needs more than restoring a map. Registers allocated on a wrong path must return to the free pool exactly once, while registers still referenced by surviving instructions must remain allocated. A committed map enables whole-pipeline restoration to retired state; branch checkpoints support earlier restart. Allocation tracking, rollback logs and checkpoint policies are alternative implementation choices with different storage and latency costs.

Acceptance tests should fill the physical pool, force stalls, commit multiple writes to one name, recover nested speculation, and repeat until any leak becomes visible. Assert no allocated destination is simultaneously free. Keep a software ownership model in the testbench so reclamation is independently checked.

15 · Scaling wakeup, selection and result routing

Our head-relative scan is an age-based policy. An unordered queue with fixed slot priority can be simpler but may delay important older work. A collapsing queue keeps age in position by shifting entries; an age matrix stores pairwise ordering instead. Both spend hardware to choose older ready instructions. Split queues group operation classes, reducing each selection problem while making dispatch balance more important. BOOM's issue-unit chapter gives concrete age-order and wakeup tradeoffs.

A centralized broadcast compares destination tags with many waiting sources. With Q entries, S source operands and B broadcasts, roughly Q×S×B tag comparisons are needed before considering routing and arbitration. Wider issue therefore increases wires and selection complexity as well as ALU count. Banking a PRF reduces some port cost but creates bank conflicts. Clustering execution near operand storage shortens communication but can add cross-cluster latency.

Fast wakeup announces a fixed-latency producer early enough for a consumer to use bypassed data. Slow wakeup waits until a result is known. Speculative wakeup predicts that a result, often a load hit, will arrive; if it does not, dependent work needs replay or cancellation. Readiness is a promise about data timing, not merely a bit to set optimistically.

Multiple functional units need arbitration when they complete together. Options include enough write ports for all results, completion queues with backpressure, or reserving future completion slots for fixed-latency units. Never drop a result when ports conflict. An iterative divider must advertise whether it can accept work and hold its result until accepted. These interface changes precede performance tuning.

16 · Fetch, branches and precise recovery

A frontend owns the next fetch address, requests instruction bytes, handles delayed responses, assembles instructions and supplies the backend. A simple first implementation stops fetching past an unresolved control transfer. This wastes cycles but avoids branch speculation while jump semantics and memory handshakes are verified. Only after that baseline works should prediction allow fetching past branches.

For a conditional branch, compare operands and select the target or fall-through. JAL writes a link and redirects; JALR forms a register-relative target with its required low-bit handling. Alignment faults and instruction access faults belong to the chosen execution environment. Add tests for target calculation independently of the predictor: prediction must not define architectural behavior.

A prediction records the guessed next PC and enough metadata to train later. Resolution compares actual control flow against that prediction. A mismatch redirects fetch, invalidates younger instructions, restores rename/resource state, and restores speculative predictor history. Fetch responses already in flight need an epoch or equivalent cancellation mechanism so stale data cannot reenter after redirect.

Precise exceptions mean older instructions may complete architecturally while the faulting instruction and younger work do not commit effects. Record the fault with its instruction and handle it when ordering permits. The ROB is the natural ordering point, but trap entry also needs architectural cause/PC state and a target handler. BOOM's ROB chapter explains its role in ordered commit and exception handling.

Checkpointing saves recovery state near a branch. A rollback log reconstructs it by undoing changes. Full flushing to committed state is simpler but can discard useful older in-flight work if not carefully staged. Choose one complete protocol; mixing a map snapshot with an incompatible free-list recovery scheme can silently leak registers or resurrect wrong-path state.

17 · Branch predictor algorithm ladder

Direction and target are different questions. A direction predictor guesses taken/not taken; a branch target buffer (BTB) associates control-flow locations with targets. A return-address stack (RAS) predicts returns using nested call structure. A fetch target queue retains metadata for blocks fetched ahead of execution. A small fast predictor can supply an early answer while a slower predictor overrides it. BOOM documents a layered frontend.

TAGE's tables use differing history lengths because some branches need short context and others correlate over a longer path. Partial tags distinguish contexts that share an index. Provider selection, alternate prediction and allocation policy are part of the algorithm, not optional bookkeeping. Read BOOM's backing-predictor explanation before turning this survey into RTL.

For a concrete modern research implementation, XiangShan documents combinations including TAGE, correction, target prediction and return prediction. Its versioned design documentation is a design reference, not a promise that every branch or release uses an identical configuration. Record a revision when comparing against it.

For perceptrons, encode history outcomes as −1 or +1, compute y = bias + Σ(weight[i] × history[i]), and predict from the sign of y. On a wrong or low-confidence prediction, move weights toward the actual outcome, with bounded arithmetic to prevent overflow. The history captured for the prediction must be available for training; using today's unrelated history would train the wrong context. The original perceptron predictor paper develops this method and its limitations.

Measure conditional mispredictions per thousand retired instructions, target misses, frontend bubbles and recovery penalty. A higher-accuracy predictor can still lose if its answer arrives too late or reduces clock frequency. Compare equal storage budgets and identical traces where possible. None of these predictors is currently implemented in this repository.

18 · Loads, stores and dependency speculation

A load computes an address and returns bytes; a store computes an address and supplies bytes. Start with ordered memory execution and a request/response interface that can stall. Address, byte mask, write data and request identity must remain valid until accepted. A load cannot be marked complete just because a request was sent. The response may be delayed or fault.

A load queue tracks outstanding reads. A store queue retains pending writes, often with independent address-ready and data-ready bits. Stores must not create irreversible memory or device effects while still squashable. A committed store may wait in a buffer before reaching the memory system; retirement and global visibility are distinct moments. BOOM's LSU documentation illustrates these queues and speculative load recovery.

Store-to-load forwarding searches older stores for overlapping bytes. For each requested byte, select the youngest older writer that supplies it. If that writer's data is not ready, wait or replay. A whole-word equality comparison is insufficient for overlapping byte and halfword accesses. Unknown older store addresses require a conservative stall or a speculation policy with validation.

Older: sw x5, 0(x1)    # Address may not yet be ready.
Younger: lw x6, 0(x2)  # Its address is ready now.

If x1 and x2 later prove equal, an early load may have read stale memory.
Detect the violation, cancel affected younger work, and re-execute correctly.

Store sets learn which loads and stores have conflicted. A store-set identifier table associates instruction sites with a set; a last-fetched-store table tracks a recent producer in that set. A load can then wait for a predicted conflicting store instead of all older stores. Violations train associations. Predictions influence scheduling only: address-based checking must still enforce correctness. The original store-sets paper describes the mechanism.

Memory-mapped I/O reads may themselves have side effects, so treating every load as harmless speculation is wrong. Add memory attributes and a conservative non-speculative path for device accesses. Test response reordering, full queues, faults, partial overlaps and a store resolving on the same cycle a younger load completes. Define which recovery event wins when a fault and a dependence violation overlap.

19 · Caches, miss tracking and prefetching

A cache divides memory into lines. Address bits choose an offset within a line, a set, and a tag. A hit requires a valid matching tag and appropriate permissions/state. Associativity provides several candidate ways per set. Replacement chooses a victim; write-back caches preserve dirty data until eviction, while write-through designs propagate writes more directly. These are independent choices from out-of-order scheduling.

A blocking cache waits for a miss to finish before servicing further work. A nonblocking cache uses miss-status holding registers (MSHRs) to track line fills and dependent requests. Requests to the same missing line can merge. MSHR capacity, refill bandwidth and writeback buffers bound memory-level parallelism. When any resource fills, apply backpressure rather than discarding a request.

Stride prefetchLearn a repeated address delta, often per instruction site, and request future deltas.Phase changes and irregular accesses reduce accuracy.
Spatial / signature-based predictionUse region patterns or recent address-delta context to predict future accesses.More metadata, aliasing and training requirements.
Best-offset prefetchScore candidate offsets using recent accesses and choose an offset with useful timeliness.Needs adaptation and throttling when candidates stop helping.

Prefetching is a performance hint, never a reason to change architectural results. Track accuracy (used requests / issued requests), coverage (demand misses avoided), timeliness and extra traffic. Wrong or late prefetches consume queues and can evict useful data. XiangShan's documented best-offset design is one concrete reference, not a universal cache recommendation.

A concrete static RRIP example uses two bits per line: on a hit, set its prediction to zero; insert a new line with prediction two; for replacement, seek prediction three and, if none exists, saturating-increment all candidates until one does. The prediction is an ordinal reuse estimate, not a cycle timer. Variants change insertion behavior or select policies dynamically. Read the original RRIP paper before choosing the exact variant and evaluating it against LRU.

Before optimizing, test hit-under-miss, multiple requesters for one line, dirty eviction during refill, and full writeback queues. Do not assume a two-port RTL array becomes a particular SRAM macro. Cache memory inference, ECC and refill arbitration require a selected implementation target.

20 · Memory consistency, atomics and coherence

Out-of-order execution is local scheduling. Memory consistency defines allowed observations of loads and stores, including between harts. Cache coherence organizes copies of a location; it does not alone specify ordering across different locations. A processor must satisfy the ISA memory model even when its internal transactions overlap or reorder.

RISC-V's RVWMO specifies constraints on observable memory behavior rather than a mandatory pipeline. Fences and atomic ordering annotations constrain permitted orderings. A conservative implementation may impose stronger ordering at a performance cost, but informal claims that “everything may reorder” are incorrect. Use the RVWMO specification and executable litmus tests when designing the LSU.

Load-reserved/store-conditional tracks a reservation and permits the conditional store only when its rules hold. Atomic read-modify-write operations require an indivisible architectural update relative to relevant observers. A local ALU read followed by an ordinary unprotected store is insufficient. Reservation granularity, invalidation events and forward-progress requirements must be specified and tested.

MESI-like protocols label cache lines modified, exclusive, shared or invalid. A write generally needs ownership and may invalidate other copies. Directory protocols track sharers; snooping protocols broadcast relevant requests. Real controllers also need transient states while requests, acknowledgments and data are in flight. Deadlock avoidance requires reasoning about response resources and channel dependencies, not just naming four stable states.

Multicore support adds a memory-system verification project. Begin with one core and a well-specified external memory interface. Add coherent sharing only with protocol tests, memory-model tests and a defined interconnect. This repository has no cache or atomic implementation at milestone 0.

21 · Translation, protection and architectural traps

A virtual address names a location in a software address space; translation produces a physical address and access permissions. A translation lookaside buffer (TLB) caches translation results. On a miss, a page-table walker reads translation structures, checks validity and permissions, and returns a translation or a page fault. Instruction and data access paths may use separate first-level TLBs.

Address-space identifiers reduce unnecessary invalidation between address spaces, but they do not eliminate invalidation when mappings change. Page sizes, page-table levels, accessed/dirty handling and privilege checks belong to the selected architectural mode. Sv32 is a possible RV32 path; choosing RV64 opens different translation schemes and is more than widening the data type.

Physical memory protection checks accesses against configured physical regions and permissions. Privileged control/status registers represent trap entry and return, interrupt control and other architectural state. A fault detected deep in a speculative pipeline must be attributed to the correct instruction and become visible in order. A younger fault should not bypass an older unresolved architectural event.

Before promising an OS boot, choose privilege modes, interrupt controllers, timer devices, memory map, firmware interface and the exact supported extensions. Those are platform specifications, not values to invent in a generic tutorial. Consult the official privileged architecture when implementing this milestone.

22 · Multiplication, division, compressed, floating point and vectors

Multiplication can use partial-product generation, reduction trees and a final carry-propagate addition; iterative implementations reuse arithmetic across cycles while pipelined ones trade area for throughput. Division can iteratively produce quotient digits or use reciprocal-based techniques. Start with a simple verified implementation and test signed extremes, divide-by-zero and overflow semantics from the selected ISA extension before optimizing the datapath.

Compressed instructions affect fetch and decode boundaries because instructions are no longer uniformly four bytes. A decompressor may translate supported short encodings into internal operations, but PC increments, cross-line assembly, fault attribution and branch targets must still reflect original instruction lengths. Do not simply reinterpret every fetched 32-bit word independently.

Floating-point execution adds rounding modes, exceptional values, status flags and exact architectural corner cases. Fused multiply-add rounds according to fused semantics rather than rounding an intermediate product separately. Floating-point register renaming and status updates must obey recovery and retirement rules. Numerical similarity to a host-language calculation is not sufficient verification.

Vector execution introduces vector length, element width, register grouping, masking and element-level progress. A vector instruction may occupy several lanes or run over many cycles. Memory faults and restart state can require preserving partial progress according to the ISA. The vector register file and load/store bandwidth make this a substantial design effort, not another ALU case.

Use the ratified extension chapters as the semantic source and maintain explicit implemented-extension metadata. None of these extensions is supplied by the baseline.

23 · Superscalar, speculation and research extensions

Two-wide dispatch needs two admissions that agree on every required resource. An accepted prefix is easier to reason about than arbitrary holes. Lane 1 must see lane 0's new mapping when dependent. Two writes to one destination must retain both correct old mappings. Wider retirement accepts an ordered completed prefix and stops at the first unfinished or faulting instruction.

Wider issue needs operation-to-port matching. If one port supports only addition while another supports addition and division, a naive assignment can waste the flexible port and block a division unnecessarily. Define arbitration and fairness, then measure whether a more complex selector is worthwhile. More lanes may lower clock frequency enough to offset higher IPC.

Move elimination can map a destination to an existing physical value instead of executing a copy, but shared physical ownership complicates reclamation. Zero idioms may create a known zero without waiting for old sources only when semantics justify it. Macro-operation fusion combines eligible instruction patterns internally while preserving their architectural effects, faults and retirement reporting.

Value prediction guesses a result to break a true-dependency wait, then validates it and recovers on mismatch. Runahead execution explores future memory accesses during a long stall while preventing speculative architectural updates. Both introduce additional validation and recovery work. They are optional research directions, not prerequisites for a good first OoO core.

Simultaneous multithreading shares queues and execution among independent architectural contexts. Every relevant map, retirement stream and recovery event needs a thread identity. Queue quotas and scheduling policy affect fairness; shared predictors and caches affect isolation. Add SMT only after a single-thread implementation has strong ownership and recovery invariants.

24 · Synthesis, timing and a real implementation target

Functional RTL is the input to implementation, not the end. Synthesis transforms the logic into gates or FPGA resources. Static timing analysis evaluates register-to-register paths under constraints. Placement and routing determine wire delays and congestion. Clock-tree synthesis, reset distribution and test structures add physical concerns that an untimed C++ simulation cannot model.

Choose an FPGA board or ASIC library before creating pin assignments, clock periods, memory macros or timing exceptions. For FPGA, inspect inferred block RAM, DSP usage and routing. For ASIC, select supported memory compilers, process corners and signoff flows. A tutorial must not fabricate a target frequency or a board constraint file without a target.

Critical OoO paths often include wakeup/select, register-file access, bypass muxes, allocation logic and recovery fanout. Pipeline these only with a defined latency contract. Retiming can alter when readiness must be announced. Clock gating should use supported cells or primitives and verified enable timing; hand-built combinational clock logic is not an adequate power strategy.

Clock-domain crossings need synchronizers or asynchronous protocols; a register in one domain is not safely consumed merely because simulation appears stable. Reset release and externally asynchronous inputs need equivalent care. If the design remains single-clock, keep that contract explicit rather than introducing unverified additional clocks.

Report implementation evidence with tool version, target, constraints, RTL revision and test workload. IPC equals retired instructions divided by cycles over a defined interval. Runtime also depends on clock frequency and instruction count. A three-stage teaching ALU is not evidence of timing closure or competitive performance.

25 · A build order with acceptance gates

  1. Understand milestone 0. Run the regression, follow a RAW chain through tags, and explain simultaneous commit/allocation without guessing.
  2. Add a conservative frontend. Fetch real instructions, implement branch/jump semantics, and stop at unresolved control flow. Verify stale-response handling.
  3. Add ordered memory. Implement access widths, byte masks, sign extension, stalls and faults. Prevent speculative device effects.
  4. Finish a chosen RV32I environment. Cover every required instruction and the trap/fence contract; compare with independent architectural tooling.
  5. Separate physical registers. Implement free-list ownership and retirement reclamation before branch checkpoints.
  6. Add speculation and recovery. Test nested control flow, oldest-event priority and late killed completions.
  7. Make memory out of order. Add queues, forwarding, conservative disambiguation, then prediction and replay.
  8. Add caches and width. Measure resource stalls before choosing queue sizes, ports and predictors.
  9. Choose extensions and platform. Add privilege, translation and software boot only against an explicit platform contract.
  10. Implement physically and optimize. Use measured timing, workload counters and verification to justify changes.

Each milestone should deliver RTL, tests, interface documentation and an updated tutorial together. The detailed repository roadmap lists exit evidence. Do not create dozens of empty modules to imply progress; add a module when its contract and behavior can be reviewed.

26 · Exercises with expected reasoning

Why must x1's mapping survive when an older x1 writer commits?

A younger unretired writer still owns the speculative name. Committing the older writer updates architectural state, but clearing the younger mapping would make later consumers read stale committed data. Compare the current map tag with the retiring tag before clearing it.

Why is storing only the architectural source index insufficient?

Another instruction can rename that index before the consumer executes. Bind the consumer to the producer identity during in-order dispatch so later name changes do not alter the value it needs.

What happens if the producer broadcasts during consumer dispatch?

The incoming operand must capture that result or resolve it through an equivalent guaranteed path. This core bypasses the current broadcast into the incoming operand. Waiting only for a future broadcast would deadlock because the producer broadcasts once.

Can we change ROB_DEPTH from eight to ten?

Not by editing the constant alone. Natural binary overflow wraps a four-bit tag at sixteen, not ten. Head/tail increments and age scanning need explicit modulus handling, plus out-of-range and wrap tests.

Can a full ROB accept a dispatch when the head retires?

A more optimized design can, but it must distinguish the old entry being read from the new entry occupying the same slot. This baseline intentionally waits one cycle and documents the throughput cost.

Why are branch checkpoints insufficient for delayed memory responses?

Restoring rename state does not prevent a response from a killed request from writing a reused destination. Request identity must include an epoch/generation or the cancellation protocol must guarantee stale responses cannot be accepted.

What experiment should precede a TAGE implementation?

Build correct recovery and a simpler predictor, measure conditional and target misses and frontend stalls, then compare alternatives under documented storage and timing budgets. Predictor accuracy alone does not determine performance.
